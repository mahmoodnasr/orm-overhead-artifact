# results/sf1 — the SF1 rerun

The SF10 campaign is complete and its files are frozen at
`results/all_results.csv` and `results/corrected/measurements/`. Nothing in this
directory is derived from them and nothing here writes to them.

    all_results.csv     generated by scripts/4-analysis/make_all_results.py --scale 1
    measurements/       raw per-query timings, append-only, one file per
                        (dbms, schema), written by scripts/2-benchmark/run_query.py

## Why the split is by path and not by a column

A measurement row is keyed by `(dbms, schema_config, query_id, framework, path)`.
That key does not contain the scale factor. An SF1 row written into the SF10
measurements directory therefore does not sit beside the SF10 row for the same
cell — it **replaces** it in every rebuild from then on, with no error and no
warning, and the resulting file looks exactly as complete as it did before.

`run_query.py` now records a `scale_factor` column so a row is self-describing,
but that is defence in depth, not the mechanism: the sixteen SF10 measurement
files were written before the column existed and carry no scale factor at all.
For them a blank means ten. For any other campaign a blank means unknown
provenance and the row is excluded.

`scripts/utils/results_paths.py` decides all of these paths, in one place, from
`TPCH_SF`. It refuses to guess when `TPCH_SF` is unset, because the guess that
would be convenient — ten — is the one that overwrites a finished campaign.

## Before anything here is cited

`dbms_version` and `orm_version` read *"not recorded - read off the running
server at campaign time (C22)"*. The version constants in `make_all_results.py`
are what the SF10 campaign ran — PostgreSQL 14.23, Django 4.2.0 — and are wrong
for this one, which runs PostgreSQL 18.6 and Django 6.0.8. Filling them from the
running server is the remaining half of C22 and must happen before an SF1 figure
appears in the paper. A stated gap is recoverable; a plausible wrong version is
not.
