## The result

Median ORM overhead against each framework's own hand-written SQL baseline,
pooled across all four database systems and both physical designs:

| Workload | Django | SQLAlchemy | $n$ per framework |
|---|---:|---:|---:|
| TPC-H (analytical) | +1.1% | +1.3% | 146 / 152 |
| TPC-C (transactional) | +115.7% | +68.1% | 40 / 40 |

That contrast — +1.2% against +92.7%, Mann-Whitney p < 1e-24 — is the largest
effect in the study. It is bigger than the framework effect, bigger than the
database-system effect, and bigger than the effect of removing every secondary
index from the schema. No system tested reverses it.

The frameworks are statistically indistinguishable under analytical load
(paired Wilcoxon p = 0.95, Cohen's d = 0.13) and clearly different under
transactional load (p = 0.005, d = 0.43, a factor of 1.7 in the median). The
Active Record vs Data Mapper question has an answer, and the answer is
"conditional on how much the database is doing per statement".

Object materialisation explains neither workload: the two largest overheads in
the study return 100 rows and one row.

### Why the story changed

The earlier PostgreSQL-only, TPC-H-only result — roughly zero overhead, no
framework difference — was not wrong. It was one denominator. Adding a workload
where the database does *not* dominate is what turned a reassuring null result
into an explanation of why the published literature disagrees by two orders of
magnitude.

## Nine defects, four of them in the corrections

Recorded in full in `docs/CORRECTIONS.md`. The four found late are the ones worth
knowing about, because each was in code written specifically to fix an earlier
defect:

- **C6** — Q11's threshold is `0.0001/SF` and was held at the SF1 constant, so at
  SF10 it excluded every group. The query still scanned, aggregated and sorted,
  so it reported a plausible time for a result of zero rows.
- **C7** — Oracle blank-pads a comparison only when *both* operands are CHAR. A
  bind variable is VARCHAR2, so every ORM equality against a CHAR column matched
  nothing while the same predicate written as a literal matched. Q2 returned 100
  rows through both SQL paths and 0 through both ORM paths, with no error.
- **C8** — the validation harness compared ORM to ORM and baseline to baseline,
  never ORM to its own baseline, which is why C7 passed every check. Now five
  checks per query.
- **C9** — four Django modules branch per vendor for date-literal syntax, and
  every branch carried the right window except the Oracle one, which in all four
  files was pinned to Q4's quarter.

## Open items, and what each would cost

**Oracle's indexed analytical configuration is 17 queries short.** Oracle Free
caps user data at 12 GB; TPC-H SF10 loads to 10.81 GB and LINEITEM's six
secondary indexes are ~1.1 GB each, so the fourth raises ORA-12954. The
working-set driver recovers the five queries that never read LINEITEM and cannot
recover the rest. Removing this needs Oracle Standard or Enterprise — and note
that the licence covering those forbids publishing benchmark results without
Oracle's consent, while the free edition's licence does not. **Recommendation:
leave it, report it as a limitation. It is already written up that way.**

**One scale factor.** The analytical medians are near zero *because* SF10 makes
the database dominant. Sweeping database-time-per-statement from microseconds to
minutes would locate the crossover point where framework cost stops being
negligible, and would turn the qualitative finding into a number a practitioner
could apply to their own latency budget. This is the most valuable follow-up and
is written up as future work.

**Idiomatic, not optimal.** Both frameworks offer bulk operations, explicit eager
loading and session batching that attack the per-statement mechanism directly.
None were used. The transactional figures are the cost of the straightforward way
of writing the code, and the thesis says so.

## Answers to your three questions

**Why do the results look scattered?**
The measurements themselves were never scattered — they have always been written
to `results/corrected/`. What I scattered was the *commentary*: RUN-LOG,
PAPER-REVISION, DATA-AUDIT, CODE-AUDIT, HANDOVER, WHERE-RESULTS-LIVE, and
several zips, each delivered as I went. That was noise and it is my fault. From
here there is one results file, this one plan, and `docs/CORRECTIONS.md`.
RUN-LOG.md, `make_master_csv.py` and `run_benchmark_fixed.py` have been retired
to `_to_delete/` because each duplicated something that already existed.

**Why was the original code not modified?**
Most of it was, in place. `django_app/queries/q09.py` and `q13.py` are edited
originals; `sqlalchemy_app/queries/` is the corrected package under the original
name. The exception is `run_benchmark_multi_orm.py`: I wrote `run_query.py`
alongside it and later retired the original rather than patching it, because the
component-synthesis code in it had to go rather than be repaired. That was the
right call for the code and the wrong call for communication — I should have
said so plainly at the time instead of leaving two harnesses in the tree.

**What is the execution plan?**

— B3, TPC-C — and on sequential machine time for Oracle, MySQL and SQL Server,
which is mine.
